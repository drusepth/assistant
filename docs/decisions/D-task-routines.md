**D-task-routines. A chore is one Task whose standing reminder, on firing, reopens it and pulls it into Today.** Resolves **Q-routines** on the ask it was waiting for: a household wanted "change the litter" and "buy cat food" on the board on a cadence, not just as a ping. Built exactly as Q-routines sketched it. There is still one durable Task row, and the cadence still lives on the Reminder (D-standing-reminders is unchanged). When a standing reminder whose subject is a Task fires, `Reminders::DispatchJob#advance` also calls `Task#come_round!`: the task reopens if it was done and moves into Today. Nothing respawns, so the Done column never fills with copies of one chore. It comes round even when the ping is skipped as stale, because a late notification is noise but the chore is still owed. The task form gets a Repeat picker (`tasks/_routine_fields`). It reads and writes the task's *routine*: its first pending standing reminder, composed through the Reminder's own picker attributes and always worded as the task's title. "Doesn't repeat" retires that one reminder and leaves any others on the task alone. Semantics are fixed-schedule (Todoist's "every!"): the cadence runs from the rule, not from when the chore was last checked off. Completing a task already kept its standing reminders, so checking the litter off this week never ends the routine.

*Why not merge Task and Reminder, or put the cadence on Task.* They answer different questions. A Task is *what* is owed and whether it's done. A Reminder is *when* to tell someone, and it also hangs on Events and on nothing at all. A routine needs both: the chore on the board, and the moment it comes back. Putting a rule on Task would duplicate the recurrence engine, the dispatcher and the missed-occurrence handling that Reminder already has. So the user sees one thing, a task that repeats, and the model keeps the two jobs apart.
