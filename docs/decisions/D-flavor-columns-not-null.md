**D-flavor-columns-not-null. A flavor column is NOT NULL, and the plain case gets a name.**
Columns that say which *sort* of row this is — `kind`, `kind_key`, `status`, `group` — are `null: false` with the plain case spelled out (`credentials.kind` "login", `feeds.kind` "rss", `spending_accounts.kind` "checking", `suggestions.kind` "nudge", now `notes.kind` "plain"). Not a style rule: in SQL, `kind != 'allergy'` evaluates to NULL — *not true* — for every row where `kind IS NULL`, so one negated query silently drops every plain row. That is exactly what emptied doctor-visit-prep's Health-notes block while D-allergy-notes was being built, and `notes.kind` was the only column in the schema shaped that way. The fix belongs in the schema, not at each call site: a defensive `where(kind: nil).or(...)` works but has to be remembered every time, forever, by everyone. `SchemaConventionsTest` enforces this against the live schema so the next one is caught at the migration rather than in a surface that quietly returns nothing. A column whose NULL means *an unanswered question* rather than a value — `notes.severity` ("not sure"), `documents.health_plan` (unpinned / pinned / banished) — is a different thing wearing the same shape: an optional attribute, not a flavor. It stays nullable, the test never asks about it because it isn't flavor-named, and nothing negates it. The test's EXEMPT list is for the rarer collision — a column actually *named* kind/status/group whose NULL is meaningful — and is empty today on purpose. — *Built.*
