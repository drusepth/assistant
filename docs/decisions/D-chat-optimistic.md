**D-chat-optimistic. A sent message renders locally before the server hears about it, and the server answers with an append, not a page.**
`ToolRunMessagesController#create` currently ends in `redirect_to run`, so every turn morphs the whole document and nothing happens on screen between the tap and the response — a few hundred milliseconds to a couple of seconds of a screen that looks like it ignored you. Two halves, and they belong together: the `chat-input` controller appends a user bubble from a `<template>`, clears the box, drops in the thinking indicator and scrolls, all synchronously *before* the fetch starts; and the server responds with a Turbo Stream append of the persisted turn instead of a page, with `ChatTurnJob` likewise broadcasting an append rather than `broadcast_refresh_to`. Because the transcript stops being re-rendered wholesale, scroll position, keyboard state, and a correctly-scoped `aria-live` announcement all come for free. The two are reconciled by a client-generated token: the optimistic bubble is `id="msg-<token>"`, the form posts the token, the server's append targets the same id, so Turbo replaces the placeholder instead of duplicating it. A failed POST leaves that bubble marked "Not sent" with a retry and **the user's text intact** — strictly better than today, where a failure loses the draft. Non-JS is unaffected: the form still posts, a non-stream request still gets the redirect, and the optimistic path is an enhancement over a working form, the same posture the send button's dimming already takes. — *Built, and half of it deliberately not: the server still answers with a redirect and the page still morphs. A turn changes more than the transcript (the composer's lock, the chips, the recap affordance, the retry button, the indicator), and five targeted streams would have traded a large regression surface for nothing the reader can see — while everything the reader *can* see, the gap between tap and response, is closed on the client alone. The token survived as a `client_token` column and is what makes the morph match the drawn bubble to the server's turn instead of swapping one for the other. One ordering fact is load-bearing: Turbo captures the request body when it constructs the submission, so the token is stamped on `submit` and the composer is cleared on `turbo:submit-start` — clearing it a moment earlier posted an empty message, a bug only the real browser found.*
