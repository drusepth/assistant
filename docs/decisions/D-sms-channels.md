**D-sms-channels. A text is a fourth channel kind, not a Twilio integration: your own modem, a commodity carrier, or Signal — whichever the household set up.**
D22 stopped at the three channels that assume nothing (webhook, Web Push, email-if-SMTP), and left "text me" to a user-run bridge. That works, but it asks the person least able to run infrastructure to run some, so SMS becomes a first-class `NotificationChannel` kind with the same shape the model layer takes toward model providers: a **registry of providers** (`SMS_PROVIDERS`), one `Notifications::Sms::*` class each, and which one a household uses is a Settings choice rather than an integration. Three ship. **gammu-smsd** is the mission-true one — a GSM modem and the household's own SIM, no account, no per-message fee, no third party in the path, and the only channel that still works when the box has no outbound internet; delivery is a **file drop into the FILES-backend outbox** (staged under a name the daemon ignores, then renamed — an atomic rename is what stops gammu reading a half-written message), chosen over shelling out to `gammu-smsd-inject`, which would need the binary in this container and would put a user-supplied number on a command line. **Twilio** and **Amazon SNS** are the commodity half, both a plain form POST — SNS's SigV4 is ~30 lines of HMAC by hand rather than the AWS SDK, because one POST should not drag a dependency tree onto a self-hosted install. **signal-cli-rest-api** joins as its own kind and is strictly better than SMS wherever the recipient has Signal: free, end-to-end encrypted, and no carrier keeps a copy. Two rules exist only because a phone is involved. **Credentials are encrypted at rest** in a new `secrets` column (`serialize` then `encrypts`, the `linked_accounts.credentials` shape) — the registry marks which fields are secret, so the controller never decides and an auth token cannot land in the plain `config` Settings renders back. And **every text is metered**: SMS is the first channel that costs money per message, so a per-channel daily cap (default 10) is checked before sending and counted only after a send succeeds, because "Active sections only" bounds *which* watchers may speak, not how much a chatty week costs. The D22 payload rule holds unchanged and gets a length bound on top — counts and titles, never bodies, truncated to two GSM segments — for the reason D22 gave about lock screens, doubled: a carrier keeps a copy of everything it delivers. — *Built: the four transports, the encrypted `secrets` column, the daily cap, and the Settings forms. Still one-way; a reply path (the signed-link design, which needs no inbound webhook and so survives NAT) is the next question — see Q-sms-replies.*
