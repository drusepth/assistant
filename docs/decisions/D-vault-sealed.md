**D-vault-sealed. The vault crypto generalizes by extraction, not duplication — and the cookie path-scope survives it.**
The diary is the second container behind the keyring, and it lands by refactoring the password vault's machinery into container-agnostic pieces rather than copying it: a **`VaultSealed`** model concern carries the item-key envelope (`write_secrets!`/`update_secrets!`/`rotate_secrets!`/`unwrap_item_key`/`read_secrets`, parameterized by AAD prefix and key-row association) that `Credential` and `DiaryEntry` both include; **`VaultSession` grows a cookie-path registry** (`COOKIE_PATHS = %w[/credentials /diary]`, one path-scoped cookie each) because widening the path to `/` would silently gut the invariant that the unlocked key transits only on vault requests; **`Keyring#reset!` iterates a registry** of sealed models' `mark_lost_on_reset!` hooks, because a hand-maintained destroy list that misses a container is a security bug (orphaned wraps that still decrypt); and `Vault::Share` takes the sealed record. `Keyring`, `Vault::Crypto`, and the unlock-rides-sign-in flow don't change at all. The extraction wave's acceptance test is the existing password vault suite passing **unmodified** — zero behavior change to passwords is the point. `VaultEvent` stays credential-shaped until diary sharing actually needs a polymorphic subject (built then, not speculatively). Full design in `DIARY_PLAN.md` §2.
