**D-landing-registry. One registry of landing kinds is what the model is told, what code validates against, what writes the row, and what the review page renders.**
The app already has three independent "the model proposed a row, code writes it" paths — `ToolRun#land_one` (note/task/event, a `case`), `Suggestion#materialize` (task/event/spending/…, five `if`s), and `Documents::Analyze#extracted_facts` (pay stubs, a whitelist constant) — and none shares a definition: when Notes grew medication and allergy kinds, none of the three learned it; when `PetFood` landed, none could propose one. Document intake (D-document-intake) would have been the fourth list, and the request that occasioned it named the real problem: *how does the upload know everything the app can store, and how does that not drift as we add more?* The answer is that the list is one object. **A landing kind is one class** (`app/landings/landing/<kind>.rb`, registered in `Landing::KINDS` on the `Tool::SLUGS` pattern) that declares its fields once — description, type, and for choice/ref fields the closed set the answer must come from — and from that declaration four things are derived rather than written: the prompt paragraph the model is shown (`Landing.prompt_block`, generated, never hand-authored), the validation of the answer into what the app already has (unknown keys dropped, dates parsed or dropped, choices matched against `Pets::CareKinds`/`Note::SEVERITIES`/`PetFood::FORMS` or dropped, refs resolved through `visible_to` or dropped), the write (`land!` — the only code that knows the row, so `ToolRun#land_one` becomes a registry lookup and the agent's prepared work can stage any registered kind the day it exists), and the preview the review page renders. A kind is never a new primitive: `Landing::Medication` writes exactly the Note the Medications form writes, and an *amendment* kind (`pet_facts`: weight, microchip, vet) updates an existing row with an old → new preview and the D16 hand-set guard. **The drift guard is a test, not a convention**: every `Landing::Base` descendant is registered (the `vault_sealed_test` shape), and every key in `Users::Export::MODELS` — the one list that already has to know everything the user owns — is either produced by a kind or named in `Landing::NOT_INTAKE` with a reason (photos, credentials, feeds, recipes-which-route-to-their-own-importer, …). Adding a primitive without deciding whether paper can produce it is a red test. Affordability follows D-no-keyword-logic's only sanctioned route — ask about less: when the generated block outgrows a small model's window, the call splits into a presence pass over kind *names* and a detail pass over the present kinds' fields, never a cheaper mechanism. Design in `docs/INTAKE_PLAN.md` §2–§4. — *Designed 2026-09, not started.*
