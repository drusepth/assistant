**Q-intake-edit-in-review. Editing landings in the review page before saving.**
Resolved before the build (2026-09): the review page (D-document-intake) **edits, not just toggles**. Each landing card is a prefilled form — the model's values in inputs rendered from the kind's field DSL (a date is the date picker with the D16 chips, a `:choice` is a select over its closed set, a `:ref` a select over the user's visible records) through `ApplicationFormBuilder`, so no kind writes a form partial. The first draft parked this as a later rung on the grounds that it doubled the form surface; it doesn't, because the registry already declares each field's type and set for the prompt and the validation, and rendering an input from that is the fourth derivation, not a second definition (D-landing-registry). What the user submits goes back through the same `validate` as the model's answer — an edited landing is checked by exactly the code that checked the proposed one — and the page is one form: every checked card posts together, a failing card re-renders with its error in place, and nothing lands until the whole page passes. Values the user changed are theirs (D16's hand-set guard) and no categorize job second-guesses them. Design in `docs/INTAKE_PLAN.md` §2/§5. — *Resolved.*
