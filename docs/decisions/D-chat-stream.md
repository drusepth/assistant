**D-chat-stream. The reply streams token-by-token, buffered, and degrades to today's behavior when the endpoint can't.**
A long tutor explanation is ten to thirty seconds of three bouncing dots while the model is producing text we throw away. `Llm::Client#chat` gains a streaming mode — an SSE reader over the `Net::HTTP` we already own, no vendor gem (D14) — used on the chat path only, since every other tool parses a complete JSON document and has nothing to gain. `ChatBase#reply!` creates the assistant message row **empty and first**, then fills it, so each flush is a Turbo Stream `update` of one bubble by id. Two guardrails are mandatory, not optional: **buffer** (one broadcast per token would push thousands of messages per reply through SolidCable — flush on a ~80ms timer or a sentence boundary), and **degrade honestly** (an endpoint that doesn't do SSE falls back to the existing single-shot call and the dots, detected rather than asked about, because a self-hosted Ollama on someone's laptop must not be broken by a nicety). A mid-stream failure keeps whatever arrived and appends the existing notice row — the posture `ChatTurnJob` already takes, so a truncated reply is visible rather than vanished. — *Designed; W4 of `CHAT_PLAN.md`.*
