**D-mirror-database. Mirrors live in their own database.**
A fourth SQLite database alongside Solid Queue/Cache/Cable holds all mirror tables (`MirrorRecord` base class, own migrations path). The primary database is the mission artifact — the small, copy-me life file — and the mirror is its opposite on every axis: derived (the mailbox is the truth; re-sync rebuilds it), high-churn (sync bursts, FTS5 triggers, nightly prunes), and elastic in size. Separating them keeps the life file small and calm, isolates mirror write churn from SQLite's single writer per file, and settles the export question: the mirror is **excluded from the D14 export by default** because it is re-syncable cache, and backup guidance stays "copy the life file." Accepted costs, stated plainly: cross-database references are soft ids resolved in Ruby (no foreign keys, no SQL joins — `person_id` on messages, item ids in promotion provenance, all tolerant of the far side being gone), and primitives never depend on mirror rows — promotion *copies* content out. Decided before the first mirror ships because it is nearly free now and a miserable data migration later. Full design in `EMAIL_PLAN.md` §2. — *Built (E1a): `mirror` database in every environment, `db/mirror_migrate`, `MirrorRecord`; soft ids proved workable (associations resolve in Ruby, purge and prune never touch primitives).*
