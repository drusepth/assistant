**D-stay-pins. A stay pins itself from its typed location, and the itinerary draws on the self-drawn basemap — for every traveller.**
The gazetteer that names the photo map's pins (D-travel-facet) now runs in reverse: `Datasets::Places#named` matches a stay's typed location against the same ~7,300-settlement file — a lazy name index beside the existing latitude bands — and saving a stay stores the coordinates when the text names a real town. Same honesty contract as ever: "Boise, Idaho" finds Boise (text after a comma narrows by country when it matches one, and is otherwise ignored — the file doesn't know states), a bare "Portland" goes to the biggest population, and "the A-frame on Route 9" pins nothing, which is the right answer. `Travel::ItineraryMap` then draws located stays as numbered pins joined by a route line, amber where unbooked, by riding `Photos::Map`'s `bounds:` seam over an **empty photo scope** — the padded window, min-span and aspect shaping, both basemaps and the gazetteer lettering all come free, and no coordinate-derivation code was duplicated. That empty scope is also the privacy argument: the route map reads no photo, so it is ordinary shared trip data that every traveller sees, while the photo map beside it stays owner-only — typed-location coordinates are what the household told the app, EXIF coordinates are what Q14 protects. The same pass gave the planned trip its missing half (D-trip-spine): `Travel::Trips#covering` keys the detector to a trip's own dates, and `TripsController#place` lets an unplaced trip whose dates have located photos earn its box — bounds, cover and label recomputed server-side like every number a trip stores, so the planned trip and the found trip end as one record with one history.
