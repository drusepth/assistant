**The photo map was measured at real library scale, then made 3.6× faster (`docs/TRAVEL.md` §4)**: the Travel hub and the map page compute everything fresh per request — the CareRadar/MonthSummary idiom, no cache — which only stays defensible if it is actually fast. It wasn't: 2,550ms for the Travel page on a 60,000-photo library. It is now 706ms, and the numbers are written down rather than assumed (`script/benchmark_photo_map.rb`, safe against a real database — it inserts inside a transaction and rolls back). **Loading rows cost more than clustering them**: a plain `pluck` of four columns builds a BigDecimal per coordinate and a TimeWithZone per photo — 750ms of allocation for values the map immediately wants as numbers — so the casts happen in SQL and timestamps stay epoch seconds, with a `Time` built only for the two ends of a pin that something is about to print (134ms; a test pins the types so a tidy-up can't put them back). **The clustering grid was allocating for every probe**: `Hash.new { |h, k| h[k] = [] }` *stores* an empty array for every cell merely looked at — nine per photo — and the neighbourhood scan built nine more on top; a plain hash with integer cell keys and an explicit loop took it 990ms → 355ms. On the trip side, a subtraction now settles the away-from-home test for the photos that are obviously home or obviously abroad, leaving only the band around the threshold to pay for a haversine (245ms → 193ms). **A fourth change was reverted for being slower**: trying the last matched pin before probing the grid sounds obviously right, since consecutive photos are usually in the same place, and measured 349ms against 283ms without it — recorded in the doc so nobody re-derives it. No cache, deliberately: the next real lever is letting SQLite do the grouping, which is a rewrite of both services and can wait for a library that actually hurts.
