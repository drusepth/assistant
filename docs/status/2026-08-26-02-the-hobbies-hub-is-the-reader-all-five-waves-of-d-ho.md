**The Hobbies hub is the reader: all five waves of D-hobby-feeds built**: the plan written earlier the same day, shipped. **W1** moves the river inside the hobby cards, under the engagement line rather than above it, and gives each hobby's own page a full-density river; `/reader` keeps every route but loses its rail row, and the unread pile moves onto Hobbies. `Hobbies::OtherInterests` is what makes the grid one loop — every feed has a hobby or has this one, so no query carries an "or untagged" branch — found and created *by slug* so a user's own "Other interests" hobby can't take the row, and `custom: false` so the lens page's remove button and `HobbiesController#destroy` (which finds through `Section.custom`) can't delete it: the invariant is protected at the controller layer for free. `Sections::Panel` grew a parent-lens fallback so a user-created lens, whose slug no class can be named after, resolves `Panels::HobbiesLens`; `#partial` now derives from the panel class instead of the section slug, which is the same string for every seeded panel and the only thing that can serve many sections at once. **W2** is the one model call: `Feeds::Classify` sees a feed's title, description, site and ten newest headlines — a site called "Hackaday" tells a model much less than five of its titles do — and its answer is matched against lens slugs that already exist, matched *before* capped so a hallucinated slug costs nothing rather than pushing out a real hobby. `Feeds::Filing` is the one place that decides where a new feed goes: hand-filed, ask in a job, or — with no model — the catch-all immediately, which is promise 3 in one line. **W3** handles hobbies arriving over months: `Hobbies::MapFeeds` treats a new hobby as a question about *every* feed already followed, takes lens ids so an OPML import creating six folders asks once, chunks at 40 feeds, and only ever adds — which is also how a hand-made tag is protected without `section_taggings` recording who made it. Its one mechanical removal is dropping the catch-all from a feed that gains a real hobby; the reverse case is bookkeeping with no model call, since taggings cascade with the section and `#destroy` has to collect the feeds it is about to strand *before* the cascade, because afterwards nothing remembers them. **W4** is the starter shelf, `config/starter_feeds.opml`: offered on the reader, the feed list and the hub, and only while there is nothing to read. It is OPML because that means no new code path — ticked rows are rebuilt into a small document and handed to `Feeds::Opml.import` — and the one thing it passes through is `create_lenses`, defaulted *on* here where the importer defaults it off, because an exported file's thirty folders are somebody else's filing system while a group ticked on this shelf is the user saying they're interested in cooking. No aggregator or FeedBurner URLs, asserted by a test, and `script/check_starter_feeds.rb` re-verifies the list against the live web (the URLs shipped unverified — the sandbox this was built in has no outbound network). **W5** is `Watcher::HobbyFromFeeds`, the second watcher off the SQL-only leash after job_scout: "these four feeds are all about birding" is not a question SQL can answer, and the answer that tried — keyword matching against a per-hobby vocabulary — is exactly what the plan cut. It reads a handful of *feeds* rather than the story firehose, needs three of them before it looks, and proposes one nudge whose accept opens Start-a-hobby: the lens is created by the tool the user ran, never by a watcher and never by a model's answer. Feed text is a stranger's XML reaching a model prompt in three new places now, and the defense is the same structural one each time — the model picks from a closed set of rows we handed it and can never name or create one. 1748 tests green, and the hub, a lens page and the empty-state shelf were driven in a real browser: ticking two starters followed exactly those two and made the Reading and Cooking hobbies that named them.
