**Flavor columns go NOT NULL: notes.kind names its plain case, and a schema test guards the rest**: the follow-up to the trap the allergies branch tripped over (D-flavor-columns-not-null). `where.not(kind: ALLERGY)` silently emptied doctor-visit-prep's Health-notes block, because a plain note's `kind` was NULL and `kind != 'allergy'` is NULL — not true — for every one of them. The first fix was defensive, a `where(kind: nil).or(...)` scope; this one removes the trap instead. An audit of all 54 `where.not` call sites against the live schema found the real story: `notes.kind` was the *only* nullable flavor column in the whole database — `credentials.kind` defaults "login", `feeds.kind` "rss", `spending_accounts.kind` "checking", `suggestions.kind` "nudge", and `care_settings.kind_key` / `goals.status` / `budget_categories.group` are all `null: false`. Notes were the outlier, and the bug was the outlier's fault, not the query's. So `notes.kind` is now `null: false, default: "plain"` with the NULLs backfilled, `Note::PLAIN` joins MEDICATION and ALLERGY in a `KINDS` inclusion validation, and `except_allergies` is back to the plain `where.not` that reads the way it behaves. No other live instance of the bug exists — the audit's other hits were false positives where the column name is nullable on some *other* table. `SchemaConventionsTest` now walks the live schema and fails on any nullable `kind` / `kind_key` / `status` / `group` column, carrying the whole explanation and the fix in its failure message; it was verified to actually fire by pointing it at a column that is legitimately nullable. That exception matters and is written down: a column whose NULL means *an unanswered question* rather than a value — `notes.severity` ("not sure"), `documents.health_plan` — is an optional attribute, not a flavor, stays nullable, and is never negated. Smoke-tested in the browser too: a note written through the ordinary quick-capture form now lands as `kind: "plain"` rather than NULL.
