**A plan for the stories inside a broad feed: watchlists the model writes and you edit (D-story-matching)**: design only — `docs/STORY_ROUTING_PLAN.md`, no code yet. D-hobby-feeds files feeds and never stories, which is right for the eight feeds that are each about one thing and exactly wrong for the two that aren't: a general news feed's birding stories are unreachable from Birding, and filing that feed under Birding would flood the hobby with the other 95%. Both of the obvious answers stay refused — a model call per story is still ~3,000 calls a month and still breaks the reader's third promise, and a keyword vocabulary *we* ship is still a promise to keep enumerating the world — so the plan is the third thing neither of them is: **the model writes the vocabulary, once per hobby, from this user's own reading**. Calls scale with hobbies (a handful per household, ever) instead of stories, and a rule that is wrong is visible on the hobby's own page and fixed by deleting a word, which is the failure mode a shipped vocabulary can never have. A watchlist is per user per hobby — private, because it is learned from private reading and a shared one would leak one member's rejections into another's river — and the rule is one sentence so it can be explained where it is edited: a term in the title, or two distinct terms anywhere, and no negative. Matching runs at ingest in plain Ruby over the items just written, skipping hobbies the item's feed already carries; no model, no FTS table, no network, and a bounded backfill when a rule changes. Authoring is one call per hobby plus at most a monthly re-author, and every candidate term is tested against the user's last 500 items before the rule saves — anything matching more than 20% of them is dropped, which is the cheapest possible eval harness running on the only corpus that matters. D-feed-reader's invariant is amended in exactly one direction ("an item's tags are its feed's tags, **plus any exception recorded on the item**"), with exceptions in their own `feed_item_matches` table rather than `section_taggings` — an item is not a primitive, a match needs a `source` so a rule edit can never overwrite a hand-filed tag, and match churn doesn't belong in the table every section page joins. `FeedItem` stays not-`Sectionable`; the hobby river gains one OR *inside* the existing `user.feeds` scope, so the reader's single authorization line doesn't move and no grant can widen what a match shows. No new queue: matched stories land in the river they belong to wearing a small tell, with one new verb — "Not this" — that deletes the match and writes the negative. Four waves, and **W1 has no AI in it at all**: hand-typed terms, offline matching, the editor, the tell and the verb, which is Google Reader's smart feed and the reason a no-model instance gets the whole user value rather than a degraded one. Embeddings are named as the real long-term mechanism and deliberately not built — `Llm::Client` speaks chat only, an `/v1/embeddings` seam is a provider-capability question — and the surface is shaped so centroid similarity can replace term matching later without changing anything the user sees.
