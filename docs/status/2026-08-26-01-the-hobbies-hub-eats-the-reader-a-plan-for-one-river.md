**The Hobbies hub eats the reader: a plan for one river per hobby (D-hobby-feeds)**: design only — `docs/HOBBIES_HUB_PLAN.md`, no code yet. The reader shipped as its own rail destination with a three-item courtesy card on the Hobbies page, which had it backwards: the river is not a place you go, it is what makes each hobby different every day. The plan turns the hub into hobby cards that each carry their own three newest unread under the engagement line they already show, gives each hobby lens page a full river, and demotes `/reader` to the everything-view reached from the hub rather than the sidebar (routes unchanged, one nav entry moves, the unread badge lands on Hobbies). The question it exists to answer is per-feed versus per-story filing, and the arithmetic decides it: a subscription is added a handful of times per household, a story a hundred times a day (228 unread across eight feeds in two days on the instance it was designed against), so `Feeds::Classify` spends one model call per *feed* and stories are never classified at all. The draft that routed broad feeds' stories by keyword match against a per-hobby vocabulary was cut before anything was built — keywords cannot cover the open space of hobbies and feeds that any number of users will bring, and a matcher fails silently for everything nobody enumerated; a vocabulary list is a promise to keep enumerating the world. The honest consequence is that a broad feed lands in one place, whole: world news becomes **Other Interests**, which is a real lens rather than an empty state, so no query carries an "or untagged" branch and no surface carries a special lane. It is created on demand by slug (a user's own "Other interests" hobby can't take it), never offered as a hobby, and sorted last. The map is maintained rather than built once: a household's hobbies arrive over months, so `Hobbies::MapFeeds` treats every new hobby as a question about *every* feed already followed, not only the ones parked in Other Interests — a feed tagged Guitar can also become Woodworking, which is the multi-tagging the lens model exists for. It takes lens ids rather than a lens (an OPML import creating six folders asks once, not six times), only ever adds — which is also how a hand-made tag is protected without `section_taggings` recording who made it — and makes exactly one mechanical removal, dropping Other Interests from a feed that gains a real hobby. The reverse is bookkeeping with no model call: taggings cascade on destroy, so removing a hobby can leave a feed with no lens, and those fall back to Other Interests in the same transaction. With per-story routing gone, so is the `FeedItem`-becomes-`Sectionable` reversal that draft carried: D-feed-reader's line holds unchanged and the whole feature costs one nullable `feeds.classified_at` column. Feed text is a stranger's XML reaching a model prompt for the first time, so the classifier picks from a closed set of existing lens slugs and can never create one. Four waves, only the second of which needs a model at all; `Sections::Panel.for` grows a one-line parent-lens fallback so hobby pages get a panel without touching any of the three files D37 protects.
