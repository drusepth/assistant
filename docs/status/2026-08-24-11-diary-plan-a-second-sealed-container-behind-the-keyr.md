**Diary plan: a second sealed container behind the keyring** (`docs/DIARY_PLAN.md`, D-diary-vault, D-vault-sealed): a private journal under the Vault sidebar group on the Album/Credential precedent — `Visible`, never `Sectionable`, and sealed one tier deeper than passwords: no AR-metadata tier at all, `entry_date` the only plaintext (locked index = calendar/streak/dates, nothing else). The password vault's machinery generalizes by extraction (D-vault-sealed): a `VaultSealed` concern from `Credential`, a `VaultSession` cookie-path registry so `/diary` gets its own path-scoped cookie instead of widening to `/`, a `Keyring#reset!` hook registry so a missed container can't leave live orphaned wraps, `Vault::Share` on sealed records — with the untouched password suite as the extraction wave's acceptance test. New crypto is one tier: a per-user diary key wrapped under the vault key, so owner reads cost a GCM unwrap not an RSA unwrap (a thousand-entry journal lists in one request on a Pi); capture-while-locked keeps the RSA-to-public-key path with opportunistic re-wrap. Postures settled in the plan: recovery kit gates the first entry (a lost diary is unrecoverable by design), emergency access excludes the diary by default behind an honest policy-not-crypto dial, per-entry read-only sharing is W4's only exception to private-absolutely, and AI reads are structurally impossible in v1 (keys never ride the job queue) with the future dial's consent shape fixed in §8 (Q-diary-ai). Waves W0–W4 planned; attachments wait on the storage seam (Q-diary-attachments).
