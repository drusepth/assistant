**The chat surface's mobile overhaul is designed (`docs/CHAT_PLAN.md`, D-chat-shell / D-chat-optimistic / D-chat-stream)**: the D29 chat is the one screen in the app judged against software the user opened an hour ago (iMessage, WhatsApp, the ChatGPT app), it is where the product stops being a filing cabinet and starts being an assistant, and on a phone it is currently the weakest surface we ship — so it gets a plan of its own rather than a CSS pass. The diagnosis is specific and file-anchored: the transcript is a `max-h-[calc(100dvh-20rem)]` scroller inside a card inside the scrolling page, which is **two nested scrollers** plus a magic number that is wrong on every device, so reaching the composer is a scroll and the composer moves between turns; `redirect_to run` morphs the whole document per message, so nothing at all happens on screen between the tap and the response; the viewport meta lacks `interactive-widget=resizes-content` (Chrome Android hides a bottom composer behind the keyboard) and `.composer-input` is 14px (**iOS Safari auto-zooms any field under 16px and never zooms back** — on its own a large share of "feels wrong on iPhone"), with no safe-area padding, no `enterkeyhint`, and no `visualViewport` handling; chrome eats nearly half the screen (browser UI + sticky header + page header + two wrapped chip rows + a three-line recap footer competing with the composer for the bottom); per-message timestamps are `opacity-0 group-hover:opacity-100`, so **a mobile user can never see when anything was said**; and a ten-to-thirty-second reply is bouncing dots while the model produces tokens we throw away. The plan is five waves — W1 the shell (the `layout:` screen/panel split with `.chat-screen`/`.chat-panel` atoms, a full-screen conversation route for the task page's panel below `sm`, a compact chat bar folding New session/Delete/Save a recap into an overflow menu, and the whole mobile-platform checklist: 16px input, safe area, `interactive-widget`, `overscroll-behavior: contain`, a guarded `visualViewport` listener, one snap-scrolling chip row); W2 instant send (optimistic client-rendered bubble reconciled with the server's Turbo Stream append by a client-generated id, a "Not sent" retry that never loses the text, `localStorage` drafts); W3 the conversation reading like one (time dividers instead of hover-only timestamps, copy on assistant turns, an unread count on the jump pill); W4 streaming (`Llm::Client#chat(stream:)` as an SSE reader over the `Net::HTTP` we already own, the assistant row created empty and filled, buffered at ~80ms so SolidCable isn't flooded, falling back to today's behavior on any endpoint that can't stream — detected, never asked about, because a self-hosted Ollama must not break on a nicety); and W5 the manifest that makes the app installable, which is a handful of lines for the largest single pixel win available since `public/service_worker.js` and `apple-mobile-web-app-capable` are already there. Two mechanical pins join `test/integration/mobile_layout_test.rb` — one scroll container per `:screen` chat, and a composer font size ≥16px, a regression invisible on desktop and ruinous on iPhone.
