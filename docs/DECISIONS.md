# DECISIONS.md

Decision log from design sessions. Format: decision, reasoning, status.

**ID convention:** decisions D1–D37 are numbered historically and keep those
numbers forever. New decisions use kebab slugs — `**D-photos-primitive.**` —
because parallel branches sharing a counter collide (D30 was claimed twice in
one day, then the renumbered D31 collided again the same day); slugs can't.
See CLAUDE.md § conflict hygiene.

## Decided

**D1. Model-agnostic; no model development or specific integrations.**
Open configuration lets users choose any local (or remote) model. Models are swappable commodities; we build the layer around them. — *Locked.*

**D2. Local-first, self-hostable, open source.**
Follows directly from mission (no chokepoint, no rented dependency, privacy for the most sensitive sections). — *Locked.*

**D3. Top-level sections:** Health, Hobbies, Education, Career, People, Money, Rights.
- "Friends" renamed → **People** to include family, communities, church, clubs, meetups (heavier caregiving/family use cases need an inviting home).
- Money subsections: Budget, Debt, Taxes, Assets, Bills, Subscriptions, Benefits.
- Rights subsections: Immigration, Renting, Voting, Disputes.
- "Disputes" chosen over "Advocacy" (nonprofit-speak) and "Appeals" (sounds like you already lost) — most self-explanatory to a stressed user. — *Locked.*

**D4. Sections are toggleable per-user; FTUE picks defaults.** — *Locked.*

**D5. Lens-over-primitives data model.**
One shared pool of primitives (Events, Tasks, Documents, People, Goals/Projects, Notes/Memory), multi-tagged by section. Sections never own separate databases. Cross-cutting views (Calendar, Today, Documents vault, Goals boards, Dashboard) fall out for free. — *Locked; the key architectural decision.*

**D6. Three modes: Organize (passive) → Tools (self-serve) → Agent (proactive).**
Also the build order and trust ladder. Agent behavior is per-section user-controlled (agent aggressiveness dials live in the same settings surface as section toggles). — *Locked.*

**D7. Situations as a first-class concept.**
Life events spanning sections ("lost my job," "eviction notice") modeled as Goals spawning multi-tagged Tasks/Events. — *Locked conceptually; design TBD.*

**D8. Household multi-tenancy.**
One self-hosted instance serves a household; each member is an independent user with their own data. Cross-user coordination (e.g., the AI booking a couple's appointments back-to-back so they can carpool) is a target capability. Household members as *contacts* (Person records) are modeled separately from household members as *users* (logins), with an optional link between them. — *Locked.*

**D9. Private by default; sharing is explicit, visible configuration.**
Every item belongs to its creator and is invisible to other household members until shared. Sharing works per-item and per-section ("share all my Money items with my spouse"). Cross-user AI features operate only over what's shared with the requesting user. We make **no moral/ethical judgments** in the product (e.g., whether parents may access children's data) — access control is user-visible configuration, never hidden defaults. People control their configuration, not us. — *Locked.*

**D10. Remote models first; local models are a config swap.**
Build against a single OpenAI-compatible chat-completions adapter (configurable base URL, key, model name). That wire format is spoken by OpenAI, OpenRouter, Groq, Anthropic's compatibility endpoint — and by Ollama/llama.cpp/LM Studio, so swapping in local models later is configuration, not code. Security/encryption hardening is deliberately deferred until after the foundation is built. — *Locked.*

**D11. Workflow packs are first-party only, for now.**
We author packs ourselves; users inherently trust first-party content. Community authoring/distribution (and the sandboxing questions it raises) is deferred. — *Locked for now.*

**D12. Sections are a database taxonomy table, not code enums.**
Single `sections` table with optional `parent_id` for subsections. Toggles, tagging, and any future re-parenting (e.g., moving Benefits) become data changes. — *Locked.*

**D13. Milestone 1 = Organize core, AI-lite.**
Full schema (households/users, sections taxonomy, six primitives, tagging, sharing grants), CRUD, cross-cutting views, section toggles. AI appears in exactly one place: document upload → summary + suggested tags. Independently useful per the "value without AI" principle. — *Locked.*

**D14. Technical stack.**
Rails 8.1, Ruby 3.3+, SQLite (the user's life is literally one file they own), Solid Queue/Cache/Cable (zero external services), Hotwire, Propshaft, Kamal + Dockerfile for the one-command-install path. Rails 8 built-in authentication. — *Locked.*

**D15. Onboarding: first-run setup + link-based invitations.**
A fresh instance redirects every visit to `/setup`, which creates the household and its first (admin) user in one form — solo users are fully onboarded there and never see invite concepts. Admins invite others by generating **signed join links** from Settings (name only; copied and sent over whatever channel the household already uses). No email delivery dependency — self-hosted instances rarely have SMTP. Tokens are single-use, expire in 7 days, die on revoke. No public signup, no account merging. Admins can promote/demote others and remove members; acting on yourself is forbidden, which structurally guarantees ≥1 admin. — *Locked.*

**D16. Capture is minimal; AI files the rest.**
The new-item forms were walls of fields (dates, goal, ~20 section checkboxes) that made the user do the machine's job. Capture is now the bare minimum per primitive — task: a title (quick-add bar on the index + minimal `/tasks/new`); event: a title and a day; note: just the body; goal: a title; person: a name plus an optional one-liner; document: just the file (title falls back to a cleaned-up file name) — and a best-effort, silent-on-failure `Categorize*Job` auto-applies section tags plus what the text implies: a task's due date ("renew passport by Friday"), an event's time of day ("dentist at 3pm" flips all-day to timed), a goal's target date, a person's relationship label, a note's title. Document analysis auto-applies its section suggestions too, but only to untagged documents — once the user has tagged one, suggestions stay suggest-and-click (D6). Anything the user set by hand — tags, dates, times, titles, relationships — is never overwritten; a mis-filed item is low-stakes and fixable in the edit form, which keeps all fields for refinement.
Date UX: date fields use the native picker (typeable) plus one-click shortcut chips (Yesterday/Today/Tomorrow/Next week/Next month) rendered server-side. Events store `starts_at`/`ends_at` datetimes but forms speak in virtual parts — a day plus optional start/end times; a blank start time *is* the all-day flag, so the checkbox is gone. Nobody types a datetime anywhere in the app. — *Locked.*

**D17. Tasks and Goals are one section; goals are AI-planned.**
Goals and Tasks merged into a single **Tasks** section (the separate Goals boards page is gone; `/goals` redirects). The two stay distinct models with distinct meanings: a Goal is a high-level outcome ("get a job"); a Task is day-sized with a clear done/not-done state. The section leads with one input — "What do you want to accomplish?" — which always creates a Goal, and `BreakDownGoalJob` (one LLM call, replacing `CategorizeGoalJob`) breaks it into 3–10 scheduled, section-tagged tasks *and* files the goal itself. Steps auto-apply (D16 discipline: silent on failure, hand-set fields never overwritten, pruning is one click); the goal page has "suggest more steps," which shows the model the existing plan and appends only what's missing. The **kanban moved from goals to tasks** with daily-workload columns **Later / Today / Done**: Today = pulled-in-by-hand ∪ due-today/overdue (so breakdown-scheduled tasks surface themselves each morning with no cron), Done is derived from `completed_at`, and "not today" bumps a due task to tomorrow so it resurfaces. Goals lost their board and their `backlog` status (now active/done, auto-finishing when the last step completes, reactivating when one reopens) and render as a progress strip above the board; task cards/rows show a flag chip for their goal. This is the mechanism Situations (D7) will ride on — a Situation is a Goal with a richer breakdown prompt. — *Locked.*

**D18. Section pages are three zones: Act / Attend / Browse.**
Every section page composes all three modes: **Act** (tool cards registered for the section — present even when the section is empty, replacing the dead-end empty state), **Attend** (pending agent suggestions tagged with the section — the pull-side slice of the Dashboard's push feed), **Browse** (the existing filtered primitive lists + section-pre-tagged quick capture). Subsection pages get the identical anatomy; subsection-registered tools also appear on the parent. Full design in `ROADMAP.md` §1. — *Provisional until the M2.1 build pass.*

**D19. A Tool is a first-party pipeline: owned context → LLM call(s) → draft primitives, suggest-and-apply.**
Two kinds: **plan tools** (Goal + multi-tagged Tasks/Events via the D17 breakdown pipeline with a tool-specific prompt — Situations (D7) are exactly this) and **draft tools** (reviewable artifact as a draft Note/Document + optional follow-ups). Tools are code (`app/tools/`, `Tool::Base` + registry — behavior is code even though taxonomy is data per D12); runs are rows (`tool_runs`: inputs, status, output, created primitives; live-updating run page). Output is always draft output — the app never sends anything externally in M2. All M2 tools are **Tier A** (reason over owned data only; no assumed web capability — the model-agnostic constraint). Full design + first tool slate in `ROADMAP.md` §2. — *Provisional until the M2.1 build pass.*

**D20. The agent proposes; the user disposes.**
The agent's only write surface is a new `suggestions` table (Sectionable; rationale, action payload, fingerprint deduping, pending/accepted/dismissed/snoozed). Signals come from deterministic **watchers** (`app/watchers/`, SQL-first, LLM only for phrasing/ranking/digest). Per-section dials on `user_sections`: **Off / Quiet (default: weekly, in-app only) / Active (daily, + Today)**. Cross-user suggestions read strictly through `visible_to` (D9). Notification channels deferred (Q10). Full design in `ROADMAP.md` §3. — *Built through M3.2 (suggestions table, five watchers including neglected-hobby, Off/Quiet/Active dials in Settings honored by weekly/daily scans) plus M3.3's phrased weekly digest (LLM phrases, never decides; silent failure). Cross-user coordination and notification channels followed in M4 — see D21/D22.*

**D21. Cross-user coordination is ordinary watchers over `visible_to` scopes.**
No household-level agent, no new data model, no new privacy machinery: a cross-user watcher queries `visible_to(user)` instead of user-owned scopes, so it structurally cannot see or reference an unshared item. Each member's agent speaks only to its own user; symmetric suggestions on both sides of a share are correct behavior; staleness resolves by dismissal (fingerprints never re-propose). Deterministic-first still applies — v1 is same-day sync, not location inference; LLM upgrades phrase the same signal, never replace it. Design in `ROADMAP.md` §5.1. — *Built (M4.4: same-day sync); the visible_to-only rule held with zero new machinery.*

**D22. Notification channels: webhook → Web Push → email-if-configured, Active sections only.**
No SMTP assumption (D15) and no third-party push dependency: a user-pasted webhook URL first (covers ntfy/Home Assistant/Matrix — the self-hoster ecosystem), per-instance VAPID Web Push second, optional instance SMTP last. Quiet means in-app only — **only Active sections may notify**; batched per scan; payloads carry counts and titles, never bodies (a lock screen is not private by default). Design in `ROADMAP.md` §5.2. — *Built (M4.3, all three channels in one pass per the 2026-08 product call). Resolves Q10.*

**D23. Silence is a product feature and an operations bug: swallowed failures get logged to `app_errors` and surfaced at `/admin`.**
Best-effort AI work deliberately hides its failures from the person who triggered it (D16) — a model that times out leaves a task unsorted rather than showing a stack trace. That is right for the user and wrong for whoever runs the box, who otherwise never learns the model has been down for a week. Every `rescue` that swallows now also calls `AppError.record` (source, error class, message, backtrace, actor, context ids); `record` rescues itself, because logging a failure must never cause one. An `ApplicationJob` safety net extends this to errors nobody rescued — an unhandled job error is still invisible from the operator's chair, so it gets recorded (best-effort user attribution from the job's arguments) before re-raising to the backend, while a record deleted before its job ran discards quietly instead of posing as a failure. Every error at `/admin` — `app_errors` rows and Solid Queue failures alike — carries a paste-ready plain-text report behind Copy / Copy all buttons, so "what broke" can be handed whole to a bug report or an AI chat. The table is a 500-row ring buffer — an unattended self-hosted instance shouldn't grow it forever.
`/admin` (household admins per D15, not a hardcoded user id) shows model-profile status, job-backend status, and the log. It reports **counts, never contents**, for other members' failed runs and documents: the admin flag is a household role, not a master key, and items stay private until shared (D9). Solid Queue is production-only here, so its panel degrades to an explanatory note rather than crashing in development. — *Provisional until the M3 watcher pass, which may want to read this table.*

**D24. Retry the model when it might answer differently; give up when it won't.**
A flat `Llm::Error` made every failure look alike, so the only options were retry-everything (four wasted calls and a delayed log entry for a bad API key) or retry-nothing. `Llm::Client` now classifies: `Llm::TransientError` for 408/409/425/429/5xx, transport failures, and invalid JSON (sampling noise — another draw often parses); plain `Llm::Error` for 4xx config problems, an unexpected response shape (not an OpenAI-compatible endpoint), and everything tools raise by hand ("no model configured", "that document is gone"). Base-class-is-permanent is the deliberate default: a new raise site fails honestly rather than retrying four times.
`RetriesModelCalls` adds `retry_on Llm::TransientError, wait: :polynomially_longer, attempts: 4` (~3s/18s/83s). Jobs keep their own rescue and open it with `raise if will_retry?(e)` — re-raise hands it to ActiveJob, falling through means last attempt, so the existing give-up path runs unchanged. Because a job stops re-raising on its final attempt, retry_on's exhaustion path is never reached and no model failure escapes to the job backend; there is also no handler-ordering subtlety to get wrong later.
`will_retry?` does second duty on user-visible state: a pending retry leaves the document "processing", the run "running", and the goal "breaking into steps…" rather than flashing a failure the next attempt may clear. One `AppError` is recorded per run, not per attempt. — *Provisional: attempt budget is a guess; the /admin log is what will tell us whether four is right.*

**D25. Hobbies are user-created sub-lenses of the Hobbies section.**
A hobby is a lens, not a Goal/Event/Note: a user-created child section of Hobbies — the first user-written rows in the D12 taxonomy (`sections.custom`, the only sections that can be removed; removing one keeps its items, which just lose the tag). Slugs share the taxonomy's global namespace (numbered on collision) and feed the LLM taxonomy listing, so categorizers and breakdowns can file straight into a hobby. Lenses are household-shared like the rest of the taxonomy; tagged items stay private per D9. Capture: the Hobbies page leads with "What do you do for fun?" (suggestion chips + free text, `Hobbies::Lens`), and the Start-a-hobby tool creates the lens too; no other tool creates lenses as a side effect. The tool registry surfaces parent-registered tools on every subsection page (and subsection tools on the parent, as before), since lenses can't be registered on ahead of time. Full design in `docs/HOBBIES.md`. — *Provisional until real-household use proves it.*

**D26. Outside accounts link per-user with scope dials that default to everything.**
`linked_accounts` (one row per user per provider) is the layer that connects the services a user already lives in — email (IMAP), address book (CardDAV), calendar (CalDAV), Facebook, LinkedIn — so the assistant can eventually draw on them. Providers are first-party registry entries in `LinkedAccount::PROVIDERS` (D11: adding a service = one entry declaring label, credential fields, scopes). Access is scope-gated per link and **defaults to full access**: linking is consent, and we store only the scopes the user switched *off* (`disabled_scopes`), so a scope added to a provider later is granted to existing links without backfill — the same enabled-unless-disabled convention as section toggles (D4). The dials are visible, user-controlled configuration on the Settings page (D9: no hidden defaults), and consumers must read through `allows?`, which fails closed on unknown scopes. Credentials are a plaintext JSON blob for now; Milestone 4's AR-encryption setup (which now covers `model_profiles.api_key`) is the obvious vehicle — encrypting `linked_accounts.credentials` with it is a pending follow-up. Per-provider sync jobs/importers/tools come per demand, each honoring the link's scopes. The first two consumers are built on a shared `Dav::Client` (plain Net::HTTP, RFC 6352/4791 discovery with `/.well-known` fallback, or a pasted collection URL directly): `People::CarddavSync` pulls vCards through `People::Import`, and `Events::CaldavSync` pulls iCalendar payloads through `Events::Import` (its REPORT carries a time-range filter matching the Ics importer's 1-month-back/12-ahead window, so servers don't ship decades of history) — the same normalize/dedupe paths as file uploads, so sync and upload can never disagree. Both run read-only, gated on the link's "read" scope via `allows?` inside the service (not just the UI); providers with a consumer name it in the registry (`sync_service:`), and one `SyncLinkedAccountJob` dispatches through that, firing on link and from a "Sync now" button, recording `synced_at`/`sync_error` on the link for the Settings card. — *Built (linking UI, scope dials, registry, contacts + calendar sync). Remaining: credentials encryption, the email consumer, recurring background sync, and OAuth (see D27).*

**D27. OAuth for linked accounts: a "Sign in with Google" button, powered by a stateless self-hostable relay.**
The UX bar is one click: nobody should have to create a Google Cloud project to link their calendar. One-click OAuth needs a registered app (client_id/secret, fixed redirect URI), and self-hosted instances have arbitrary URLs — so *some* shared endpoint must exist. The mission constraint is that it must not become a landlord. Resolution (Home Assistant's account-linking pattern): the project runs a **link relay** — a tiny, open-source, deliberately *stateless* service that (a) owns the registered OAuth app and its secret, (b) hosts the one fixed redirect URI, bouncing the provider's callback to the instance URL carried in `state`, and (c) performs the code→token exchange and hands tokens straight to the instance, storing **nothing** — no accounts, no tokens, no logs of user data. Landlord-proofing is structural, not promised: the relay's code ships in the open, the instance's relay URL is a config value (default = project-hosted, point it at your own deployment to exit), and **bring-your-own credentials remain as the escape hatch** — paste your own client_id/secret in Settings and the instance runs the whole flow itself, relay never involved. A stateless relay you can swap out is infrastructure; only a mandatory one is a chokepoint.
In-app design when we build it: (1) registry entries grow an `auth:` kind — `:fields` (today's forms) or `:oauth` with a **scope map from D26 scope keys to provider OAuth scopes**, so the visible dials become the actual consent requested — unchecking "Read your calendars" before connecting means the token literally can't read calendars, stronger than local gating; (2) authorize + callback routes with `state` CSRF and a small `Oauth::Client` (plain Net::HTTP, mirroring `Llm::Client`/`Dav::Client`) handling the relay handoff, direct BYO exchange, and refresh; (3) tokens per-user on `linked_accounts.credentials` (access/refresh + expiry), optional household `oauth_apps` for BYO; (4) a first-class **Google** provider exposing calendar/contacts (and later gmail) scopes under one link, whose sync consumers reuse the existing importers.
Costs and honesty: the shared Google app needs Google's verification to escape the 100-user cap and scary interstitial — free review for "sensitive" scopes (Contacts, Calendar), but Gmail's read scopes are "restricted" and require a paid annual CASA security assessment, so the Google provider ships **contacts + calendar first, Gmail later** (app-password IMAP already covers Gmail mail meanwhile). OAuth does **not** unlock Facebook friends or LinkedIn connections — closed to non-partners regardless of auth, and a shared FB/LinkedIn app would also need platform review for near-zero data in return; those stay official data-export files through the file importers, and their registry entries should say so rather than promise sync. Sequencing: relay + Google provider land together when Google sync is next up; DAV + app passwords already cover iCloud/Fastmail/Nextcloud today. — *Direction locked (relay + BYO escape hatch); build not started.*

**D28. Tools compose by routing, not by calling each other.**
A tool's run `output` may carry a sanitized `next_tools` payload — `{slug, inputs, reason}` prefills validated against the registry and the target's declared inputs (`Tool::Base#store_next_tools`), capped and deduped — rendered on the run page as next-step cards linking to prefilled invocation forms (the same prefill "Run again" uses). `ToolRun#next_steps` re-resolves slugs at read time so a retired tool can never break a page. **Decode-this-letter is the universal front door**: it triages any scary document into plain language (what it is, what happens if you do nothing, the options), files the note by the model's own classification plus the document's sections, lands stated deadlines as all-day calendar Events, and *offers* the specialized response tool with the document attached by code — model output never carries database ids. That is how low-frequency, high-stakes tools (appeals, debt responses, deposit demands) get discovered at the moment of crisis instead of in a menu; entry points live on document pages and vault rows. No tool ever invokes another tool — the user always clicks through a form (trust-ladder discipline). Full design in `TOOLS_PLAN.md` §2/S2. — *Built (TOOLS_PLAN wave 3).*

**D29. Chat is a tool kind, not a separate feature.**
Third tool kind `:chat` (after draft/plan): one new table, `tool_run_messages` (role user/assistant/notice — a notice is the app speaking after a failed turn, shown in the transcript but never sent to the model), under the existing `tool_runs`. The run page doubles as the chat surface; `ToolRunJob` generates the opening assistant message from owned context and `done` means *live* (composer stays open; turns run through `ChatTurnJob`, deliberately un-retried — mid-conversation, a visible notice the user retries by typing beats silent background retries). Context stays lean (system prompt + last 30 conversational turns) for the model-agnostic constraint. Primitives land only via an explicit "Save a recap" (`ChatRecapJob` → one filed Note recorded on the run) — no auto-writes, per D20. The tutor (Education) is the proving tool, and recap Notes are what give future sessions continuity — the owned-memory moat working as designed. Full design in `TOOLS_PLAN.md` §2/S3. — *Built (TOOLS_PLAN wave 5).*

**D30. Task pages host a conversation, and tasks hold an answer.**
Plenty of tasks are mental work — decide, brainstorm, draft — that can be *done* in a chat, so every task page embeds the D29 chat surface (extracted to a shared partial) via `task_chat`, a sectionless chat tool bound to its task through a new polymorphic `tool_runs.subject` instead of a form input. The opening costs nothing: the capture-time model calls that already run per task (`Tasks::Categorize` on quick capture, `Goals::BreakDown` on goal planning) now also return per-task `guiding_questions` — stored coaching questions the page shows as the assistant's opening turns (stock fallback otherwise), with the run created lazily on the user's first message, so a task page never spends a model call until the user talks back. The outcome gets a durable home, `tasks.resolution`: an answer card on the task page (save, or save-&-complete — writing the answer is how a mental task finishes), and the chat's recap verb repurposed — "Save as the answer" distills the conversation onto the task instead of filing a Note. Openers and answers ride the existing privacy walls: conversations are owner-only, the saved answer follows the task's sharing.

**D31. Health leads with logistics; the care radar is a derived view; metric streams stay out (for now).**
The Health page's lead panel — per-kind routine-care status (checkup/dental/vision: booked / on track / due / not tracked) — is `Health::CareRadar`: deterministic keyword classification over the user's own Health-tagged events, zero new schema, so the radar can never disagree with the calendar it reads and every existing feed (CalDAV sync, imports, quick capture) feeds it for free. Classification is conservative (an unplaceable event counts as nothing rather than the wrong thing) and own-events-only (a spouse's shared appointment is not your checkup). The checkup-cadence watcher rides the same classification per kind under stay-in-touch signal discipline — per-kind nudges only with per-kind history, accept opens find-care prefilled; the zero-history generic nudge survives unchanged. Insurance is vault documents surfaced by keyword (`Health::Coverage`) plus three Tier-A tools (find-care, insurance-explainer, compare-plans; Q3's coverage-here/disputes-in-Rights boundary holds). Wearable/fitness sources are deliberately deferred: Google Fit's API is dead, Health Connect is on-device-only, Apple Health exports are manual files — the durable assets are appointments and paperwork, already connected. Full design in `docs/HEALTH.md`. — *Built.*

**D32. Mental health ships as support, not therapy.**
The mind half of Health (docs/HEALTH.md §6) is three entry points on the Health page's Mind card: **check-in** (chat kind — guided modes via quick replies: unpack a stressor, breathing/grounding one step per turn, prep for a real therapy session; "just listen" honored as-is), **start-a-calm-practice** (plan kind — meditation/yoga/walks as tiny, scheduled, nothing-to-buy steps through the shared breakdown), and **find-a-therapist** (find-care prefilled — no new tool). The boundary is the Tier-A capability-honesty rule at its highest stakes: an LLM chat is not a therapist and is never presented as one — the system prompt forbids diagnosing, naming suspected conditions, and medication advice, and steers warmly toward a human therapist when things sound heavy; the one guardrail that must not depend on model behavior doesn't — a code-appended crisis notice (988 / local crisis line) opens every session, visible in the transcript, never sent to the model — and the support-not-therapy line prints on the Mind card itself. Recaps are explicit-save Notes filed under Health that feed the next session's prompt (continuity without surveillance). Deliberately unbuilt: mood inference, any agent nudge about mental state, and stored clinical labels the user didn't write. — *Built.*

**D33. Chat transcripts are ephemeral; recaps are the record.** *(resolves Q13)*
Tool runs grew a Delete button (chat copy: the transcript is gone for good; saved recaps stay) — for check-ins that's a trust feature, since the transcript is the most sensitive text in the app. `PruneChatTranscriptsJob` (weekly, Solid Queue recurring) deletes chat runs with no message in 90 days, whole — transcript and history entry — while recap Notes live on as ordinary owned notes; draft runs are history and are never pruned. Transcripts stay out of the M4 export: the recap is the durable, portable artifact, chosen explicitly (D20), and that's the memory contract — what you saved is yours forever, what you merely said evaporates. — *Built.*

**D34. Jurisdiction is one household-level free-text field.** *(resolves Q12)*
`households.region` ("Texas, USA"), admin-edited in Settings next to the model profile (the D15 admin split). Tools read it through `Tool::Base#region_line` — injected into find-care, insurance-explainer, compare-plans, and deposit-demand prompts when present; blank means tools keep asking or use `[BRACKETED PLACEHOLDERS]` exactly as before. The benefits screener keeps its own required state select (a free-text region can't safely map to a programs list). Free text over a country/state enum because the target audience is global self-hosters and the consumer is a prompt, not a join. — *Built.*

**D35. The care radar is tunable, correctable, and household-visible — and kids are users.**
Three escape hatches for the derived view (extends D31): **tuning** (`care_settings` — mute a kind, override its interval, add custom kinds that classify by their own label, whole phrase only; a missing row means registry defaults), **correction** (`events.care_kind` — a "Counts as" select on health events; the user's word beats the keywords, and `"none"` excludes an event from the radar entirely), and **household care** (each member's care lives on their own account — children included, as ordinary users — and the Health page shows other members' radars computed over exactly the events they share with you: `visible_to` is the only read path (D9/D21), each member's own settings apply, and a member who shares nothing doesn't appear). Booked tiles also route to doctor-visit-prep prefilled, and the Health Act zone hides the five tools the lead panels already carry with better context. — *Built.*

**D36. A medication is a Note with a kind, plus a refill Event.**
No new primitive: the Medications card files a Note (`notes.kind = "medication"`, name as title, dose/schedule as body) and optionally an all-day "Refill …" Event, both under Health. Every existing surface then works unpaid — renewal-radar gives refills lead time ("refill" keyword, Health section), doctor-visit-prep reads the med list because it already reads Health notes, meds export/share as notes, and refill events are radar-excluded by code (`care_kind: "none"`). Deliberately not built: dose-time reminders and adherence tracking — an assistant that nags nightly gets turned off. `notes.kind` is a primitive-level attribute (like `events.care_kind`), not a section-owned table, so the lens model holds. — *Built.*

**D37. Section pages compose per-section panels by convention.**
Born from a merge: the Hobbies, subsection-tile, and Health buildouts all edited `SectionsController`, `sections/show.html.erb`, and `SectionsHelper`, and collided. Now a section's lead panel is discovered, not wired: `Sections::Panel.for(section, viewer)` resolves `Sections::Panels::<Slug>` (nil for sections without one — they get the generic subsection browse grid), the panel object carries all section-specific page data as memoized methods plus `hidden_tool_slugs` for Act-zone curation, and the view renders `sections/panels/_<slug>.html.erb` with the panel as a local. Building out a section therefore adds files (a panel class, a panel partial, services, tools, watchers) and edits only registries — two section buildouts in parallel touch disjoint files. The shared page files change only when the *anatomy* (D18) changes. — *Built.*

**D-photos-primitive. Photo is the seventh primitive; albums are containers; sharing rides access grants.**
A photo is not a Document (no text pipeline, high volume, grid-and-lightbox browsing idiom, its own joins for albums and people), so `Photo` joins the primitive pool — `Visible` + `Sectionable`, multi-taggable, surfaced through a new cross-section **Photos view** (timeline grid), not a new section. **Albums are user-owned containers** (`albums` + `album_photos`), not sections — deliberate curation, not filters — and are themselves `Visible`. Sharing adds no new mechanism: the photo read path gains one clause mirroring the section-grant clause — a photo is visible to a holder of a grant on a containing album when the grant's grantor is the photo's owner — so `AccessGrant` stays the single sharing mechanism and `visible_to` the single read path (D9). "Share with the whole household" is a convenience button that bulk-creates ordinary per-member grants. Ingestion is deterministic and LLM-free (EXIF date/GPS, checksum dedupe, preprocessed variants); people-tagging is manual (the Q8 lesson). Full design in `PHOTOS_PLAN.md`. — *Built (all five waves).*

**D-storage-seam. Blob storage is a config seam: pick a service the way you pick a model.**
Model-agnosticism gets a storage twin: `config/storage.yml` grows an **`s3` service defined entirely from ENV** (`STORAGE_ENDPOINT`/`REGION`/`BUCKET`/keys/`FORCE_PATH_STYLE`) — one shape covering AWS S3, Cloudflare R2, Backblaze B2, and self-hosted MinIO, since S3-compatible is the protocol and Amazon just one vendor — selected by `ACTIVE_STORAGE_SERVICE` with **local disk remaining the zero-config default**. Uploads are Active Storage **direct uploads** (browser → bucket, documented CORS policy) so photo batches never funnel through the Rails process; delivery stays redirect-mode short-lived signed URLs behind `visible_to`-scoped pages; migration local→S3 is the documented mirror-then-flip path. Full design in `PHOTOS_PLAN.md` §2; setup docs in `docs/STORAGE.md`. — *Built.*

**D-people-dashboard. The People page is a relationship dashboard; the Address Book is the roster.**
The People section page stops listing Person rows (the grid duplicated the Address Book, and a synced address book drowned it in acquaintances) — a one-line Address Book link replaces it, and the three surfaces divide cleanly: Address Book = everyone + import/sync + CRUD, person page = the per-person CRM (profile, notes, log contact, Reconnect), section page = the social dashboard, shipped as the People lead panel under the D37 convention (whose base gained `hidden_browse` — the browse-zone counterpart of `hidden_tool_slugs` — so a panel can replace generic cards it renders with better context). The dashboard's subject is the **circle, not the rolodex**: `people.keep_in_touch` (explicit, manual, set from the person page or the section's "Who do you want to stay close to?" capture card — the Q8 no-inference rule extended, since an import must not turn 300 contacts into 300 obligations) selects who appears; `last_contacted_on` stays the only recency signal, and flagged-but-never-logged people show on the page but never trigger the watcher (no signal, no nudge). The stay-in-touch watcher is circle-scoped, with the migration backfilling the flag wherever `last_contacted_on` is set (logging contact was the opt-in until now) so nobody's nudges change on upgrade day; the circle itself is personal (own people, not `visible_to` — the flag is the owner's intent). The panel is capture / Coming up (birthdays off `people.birthday` + People-tagged events) / Your circle (stalest first, one-tap Log contact + Reconnect) / groups (People's sub-lenses — D25 generalized into `Sections::Lens`). Full design in `docs/PEOPLE.md`. — *Built (the split, birthday radar, the four-tool slate + caregiver/bereavement Situations, groups); Q17 links, the afterglow watcher, the cadence upgrade, and community tooling remain open behind explicit wait conditions.*

**D-career-signal. Career signal climbs a ladder: granted data first, manual logging always, inference never.**
The section's substrate is a **comp timeline** plus a **win log**, fed from three rungs. Rung 1, granted data: pay stubs are ordinary vault Documents and the analysis pipeline grows career-aware extraction (employer, rate, gross/net, hours, overtime, deductions) — a rate change against the previous stub lands as a comp-change Event automatically with provenance named (D16: the assistant does the filing; ambiguous reads become suggestions per D20); W-2s give annual ground truth; the LinkedIn official data export bootstraps the work-history profile and People; payroll/application email joins when the D26 IMAP consumer lands; bank-deposit signal joins when Money grows a transactions layer. Rung 2, the always-available floor: one-tap **comp-change Events** ("Raise: $19 → $21/hr") and one-line **win-log Notes** (quick-captured per D16) — manual and extracted entries form one timeline, manual winning conflicts; the win log stays manual-first because accomplishments live in the user's head before any system. Rung 3 is where Q8's actual lesson lives: the app never *guesses* — every nudge cites its source, and no granted or logged signal means no nudge, only a one-time invitation to start. Pay data is maximally sensitive, so D9 does the work: private by default, unshared comp never read cross-user, exportable and deletable like everything owned. No schema beyond extraction storage; tools read it all through `section_context`. Full design in `docs/CAREER.md`. — *Provisional until stub extraction accuracy and the capture habit prove out.*

**D-public-datasets. Public data ships as local datasets: seeds + refresh + import, staleness always visible.**
Between owned data and the live web sits published public data, and it is served **locally**: a two-layer lookup (`storage/datasets/` — written by `RefreshDatasetsJob` or an admin file import — wins over `db/datasets/` seeds), with every consumer displaying the data's vintage. The repo seeds only what is small and stable (the CPI-U annual-average series); the OES/OEWS national wage table ships **without** a seed and arrives via the refresh job (BLS API for CPI, the published national zip parsed by a minimal streaming xlsx reader for wages) or via `/admin`'s file import for air-gapped installs — we never bundle numbers we can't verify at build time. Consumers degrade to absence, not to guesses: no dataset → the placeholder behavior the tools already had. First consumers: the real-terms-drift watcher (CPI × the D-career-signal comp timeline, pure arithmetic at nudge time) and the raise case's buying-power and closest-median lines. Non-US datasets are additions to the same layer, not a redesign. — *Built.*

**D-career-web. The web arrives on three leashes: app-side fetch, a declared model capability, and ask-then-send.**
(1) **App-side fetch is the floor**: `Web::Fetch` — deterministic code fetching one user-supplied URL (size- and redirect-capped, private-address ranges refused via resolver check, text-only extraction) — powers paste-a-listing-link inputs and the scout, and works identically on frontier APIs and local 7Bs. (2) **Model-side browsing is a declaration, not a discovery**: `model_profiles.web_capable`, an admin checkbox for providers with built-in search; prompts then relax never-assert-current-facts into look-it-up-and-cite. (3) **The job scout** is the first sanctioned exception to D20's SQL-only watchers: it fetches per-user `job_feeds` (RSS/Atom, Greenhouse/Lever public boards, USAJobs — feeds and open APIs only, nothing ToS-fraught) and makes one ranking call over the Career+Hobbies+Education context; the **write surface is untouched** — suggestions only, one per posting ever, accept opens Tailor-my-application prefilled. (4) **Auto-apply is ask-then-send, email only**: the compose panel on a Tailor-my-application run is the review — the user's own linked mailbox, their edits, one explicit click; a sent application lands as an Applied Event + follow-up task. No ATS form automation, and nothing the app initiates sends anything. — *Built.*

**D-household-profile. The household is a first-class object with its own page and its own dashboard hero.**
Two halves of one idea. (1) **A household profile page** (`/household`, admin-edited under the D15 split, readable by everyone) holds the facts that belong to the house rather than to a person: name, tagline, banner, mailing address, `region` (D34, unchanged and still the only jurisdiction signal), phone, own-vs-rent, move-in date, and time zone — plus the member roster and invite links, which moved off personal Settings, where they never belonged. The bar for a field is a **named consumer**, not completeness: address + phone feed `Tool::Base#sender_address_block` (opt-in per tool — a street address is the most identifying thing here, so it reaches the model only where a letterhead needs it; deposit-demand is the first), `time_zone` sets `Time.zone` for every request and job (before this, "due today" flipped over mid-evening for most of the planet), own-vs-rent decides which housing help is relevant, and move-in date drives the anniversary and lease-clock math. Address stays **free text on the D34 argument** — the consumer is a prompt and a letterhead, not a join, and the audience is global self-hosters whose address shapes don't agree. (2) **The dashboard leads with a household hero** that absorbs the old page header: greeting, household name, tagline, member avatars, and up to three *highlights* — a circle birthday (D-people-dashboard scoping: an imported address book must not become a birthday firehose), the home anniversary, an on-this-day photo from the library. `Households::Hero` computes all of it from owned data — no LLM call, no network, nothing to configure before it says something warm — and the rule for a highlight is that it must be **true today and about this household**: no streaks, no scores, no manufactured milestones, and a quiet day simply greets you rather than filling the space. Deliberately not stored: household income and size (the benefits screener asks, and both are sensitive), landlord and utility contacts (those are People and Documents), and a home-inventory blob (that's Notes) — each would have been a field with no consumer. — *Built.*

**D-user-avatars. One uploaded photo per member, rendered through one component, on every surface that names a person.**
Households are the one place this app is social, and the member list read like a spreadsheet: initials in a tinted circle, three people who all live together reduced to `AB` / `BS` / `CJ`. Members upload a photo in Settings (`PATCH /avatar` — no id in the route, so nobody can change how another member appears, admin or not), stored as `has_one_attached :avatar` with a single 200×200 WEBP `:thumb` variant; the original is kept for export but never served, so a phone-camera JPEG can't end up behind a 24-pixel sidebar circle. Three choices are the substance. (1) **The initials circle is the fallback, not the legacy path** — `Ui::AvatarComponent` draws the photo when there is one and exactly the old circle when there isn't, so an instance where nobody uploads anything looks precisely as it did, and the feature costs a self-hoster nothing to ignore. (2) **One component, every surface** — sidebar, dashboard household strip, member roster, Address Book rows, People hub, sharing controls, vault sharing and emergency contacts, admin storage rows. "Everywhere" is the whole feature: a photo that only appears on the page you uploaded it from is a preference, not an identity. `test/integration/avatar_surfaces_test.rb` asserts each surface once, so a new one that hand-rolls a circle gets caught. The **provenance sweep** is the same claim carried to its end: `shared/_item_chips` is one partial reaching all fifteen primitive rows and show pages, so `from Bea` on a borrowed task, note, event, document, photo, goal or contact now leads with her face — and the same marker lands on shared vault entries, album cards and pages, shared photo tiles in a grid that previously said *nothing* about ownership, and shared events in the calendar month grid, which is the surface a household calendar exists for. `Ui::UserLabelComponent` is the avatar-plus-name pair, with the wording as block content, because what varies between "from Bea" / "by Bea" / "shared by Bea — read-only" is the sentence, not the structure. Two rules kept the sweep from becoming decoration: **only what isn't yours is marked** (a badge on every tile is a badge carrying no information), and **prose stays prose** — an avatar dropped mid-sentence ("ask Bea to re-share it") is worse than the name alone. (3) **A Person wears its linked member's face, never a borrowed one** — a contact linked to a household account (D8's `linked_user`) shows that account's photo; an unlinked contact keeps initials. Contact photos are a Person feature and would need their own field; inferring one from a name match would repeat exactly the mistake Q8 refuses. The avatar leaves with the user in the D14 export (original bytes, named in the manifest), and it is deliberately **not** a Photo: the photo library is owned by a user and browsed as memories, while this is chrome the whole household sees. Not built: cropping/rotation UI (upload a square, or accept the centre crop), gravatar-style remote lookup (a third-party call keyed on an email hash, which is the opposite of local-first), and per-household default art. — *Built.*

**D-household-reset. Owning your data includes throwing it away: /admin can empty the household back to the signup form.**
A self-hosted instance is also its own staging environment — there is no `db:reset` on a box you reach through a browser, and the fastest way to see onboarding a second time is to be a new instance again — so trying the app out otherwise leaves permanent debris. `/admin` gains a reset that destroys the household whole: every member account, every item they own, every uploaded file (purged inline, not `purge_later`, so the storage panel is honest immediately), and the user-created lenses and error log that sit *outside* household scope — those last two only when the wiped household was the last one on the instance, since sections have no `household_id`. The confirmation is a **typed word, not a dialog**: a click-through is muscle memory by the third reset. It deliberately takes the admin's own account too — landing back on the first-run form is the entire point — which makes it the one action in the app where an admin destroys another member's private items, so it stays admin-gated, logged, and paired in the copy with Settings → Export, the other end of the same ownership claim (D9's flag is a household role, not a master key, and this is the single sanctioned exception — it reads nothing, it only deletes). Not built: a keep-my-account "clear items only" variant, and any environment gate — self-hosters run their instance in production mode, and gating the button there would hide it from exactly the person it's for. — *Built.*

**D-mirror-layer. High-volume external streams are mirrored, not imported.**
Email (and future firehose sources: transactions, chat exports) lands in a per-source **mirror** — owner-private cache tables with real columns, outside the primitive pool, outside `Visible`/`Sectionable`, unreachable by grants, with user-configurable windowed retention (default 90 days, up to "everything"). Mirror rows become primitives only by **promotion**: an explicit user click or an accepted suggestion, with provenance recorded (`email_message_items`). Mirrors are not silos, though: they feed deterministic, read-only signals *outward* — messages match to People at ingest, outbound mail can (opt-in) advance contact recency, receipts/renewal notices can fuel watchers later — but nothing ever writes a primitive from a mirror without a human click. Because a mirror ingests **attacker-controlled text** that flows into the model, the hostile-input rules travel with the pattern: model output from mirror content is validated labels only, notification payloads are code-built from metadata (never model prose), and answers over mirror content cite their sources. Low-volume identity-shaped data (contacts, calendar) keeps importing directly into primitives as today. Mirror tables live in the dedicated mirror database (D-mirror-database). This keeps the lens model clean (D5), makes mail privacy structural rather than policied (D9 — no `visible_to` path exists to leak), and gives promoted attachments the whole existing pipeline (analysis, decode-letter routing) for free. Full design in `EMAIL_PLAN.md`. — *Built (E1a/E1b): the mirror, tombstoned deletion, promotion with provenance, People matching, and opt-in contact recency all landed as designed; the structural-privacy claim held — no mirror model includes Visible or Sectionable.*

**D-email-monitoring. Email monitoring rides the existing agent rails, with dials on the source and a deterministic feedback loop.**
Triage is LLM labels **on the mirror only** — it never writes primitives (D20 discipline; stated deadlines become pending suggestions, not Events) — and it runs *behind* deterministic pre-emption: `email_sender_rules` (vip/mute, written by one-click "Not important"/"More like this" feedback on digest rows and alerts, editable in Settings per D9) decide before the model is ever called, so week-one misfires become week-two accuracy through rules, not through hoping the model guesses better. Triage applies to **live-sync arrivals only, under a per-link daily budget** — backfilled history is browse/search/promote-only (labeled lazily on request), so linking a decade of Gmail costs neither an hour of LLM calls nor a single stale alarm: the alert path is structurally unreachable from backfill. The daily digest is deterministic selection + LLM phrasing (the `Users::WeeklyDigest` recipe), merged across accounts, delivered at a user-chosen time, **silent when empty**, body in-app, notification a D22 pointer (counts and header-derived titles, never bodies or model prose). Urgent alerts are the one immediate path — triage-flagged time-sensitive mail, **re-confirmed by a second skeptical LLM call**, → `NotifyJob` now — capped per day, one per thread, off by default, payloads code-built from headers; a user webhook (ntfy/Twilio) is how "text me" stays self-hosted. Boomerang is a **family** of deterministic watchers — user-armed ("remind me if no reply by ___", no AI), inferred no-reply (gated on triage's `expects_reply` label; no model → quiet, the Q8 lesson), and the inverse (mail you never answered that expected one) — whose accepts open a draft-only follow-up tool. Nothing is ever sent on the user's behalf (Q19). Email is a **source, not a section**, so its dials (digest + time, alerts, AI processing, contact recency, mirror window, own addresses, pause) live on the linked-account Settings card, not on `user_sections`; multi-mailbox users get one link per mailbox (`multi: true` providers with labels) and every surface merges across them. Full design in `EMAIL_PLAN.md`. — *Built (E2–E4, plus E5's cited ask-your-email and E6's optional IDLE listener): triage validation, the budget, sender rules, the double-confirmed capped alerts, and all three boomerangs shipped as designed; the eval corpus (`bin/rails email:triage_eval`) is the ongoing quality gate.*

**D-mirror-database. Mirrors live in their own database.**
A fourth SQLite database alongside Solid Queue/Cache/Cable holds all mirror tables (`MirrorRecord` base class, own migrations path). The primary database is the mission artifact — the small, copy-me life file — and the mirror is its opposite on every axis: derived (the mailbox is the truth; re-sync rebuilds it), high-churn (sync bursts, FTS5 triggers, nightly prunes), and elastic in size. Separating them keeps the life file small and calm, isolates mirror write churn from SQLite's single writer per file, and settles the export question: the mirror is **excluded from the D14 export by default** because it is re-syncable cache, and backup guidance stays "copy the life file." Accepted costs, stated plainly: cross-database references are soft ids resolved in Ruby (no foreign keys, no SQL joins — `person_id` on messages, item ids in promotion provenance, all tolerant of the far side being gone), and primitives never depend on mirror rows — promotion *copies* content out. Decided before the first mirror ships because it is nearly free now and a miserable data migration later. Full design in `EMAIL_PLAN.md` §2. — *Built (E1a): `mirror` database in every environment, `db/mirror_migrate`, `MirrorRecord`; soft ids proved workable (associations resolve in Ruby, purge and prune never touch primitives).*

**D-spending-mirror. Transactions are the second mirror source; statements are vault Documents; spending exports.**
Bank transactions are exactly what D-mirror-layer was built for (high-volume, derived, re-importable, owner-private with no `visible_to` path), so the ledger lives in the mirror database: statement files (CSV with saved per-account mapping, OFX/QFX with bank ids) are ordinary vault **Documents** — the durable, exportable artifact — fanned into `spending_transactions` rows; manual quick-log and (later) email-receipt rows join them. Dedupe is bank id else (account, date, amount, descriptor) fingerprint, deletions are tombstoned, and own-account transfers are flagged and excluded from spending math (the double-count trust-killer). No aggregator chokepoint: Plaid-class connections are rejected for v1 on the D27 argument; the import ladder is manual floor → statement files → receipt suggestions → open/self-hostable rails someday (Q-bank-connections). Two deliberate deviations from the email-mirror defaults, reasoned: **retention defaults to keep-everything** (rows are tiny; years of history is where trends and price-hike detection come from) and **the D14 export includes `spending.csv`** — bank portals age statements out, so unlike a mailbox the mirror here becomes the only copy. Full design in `docs/MONEY.md` §2. — *Built (B1, plus B5's receipt path): the mirror, tombstoned deletion, transfer exclusion, and the OFX/mapped-CSV import landed as designed; the export carve-out shipped. Receipts became the third row source (`source: "email_receipt"`) exactly as the mirror-to-mirror rule predicted — deterministic read, suggestion, click.*

**D-budget-envelopes. A budget is user-owned monthly envelope targets over the ledger's own categories; month math is derived; rules before model.**
`budget_categories` (Needs/Wants/Savings-&-debt groups + optional income rows, `monthly_target_cents`, `target_set_by` hand-set guard) double as the categorization target — one list, two jobs, no parallel taxonomies. Month math (`Money::MonthSummary`) is a derived view over the mirror ledger, never stored (the CareRadar idiom: it can't disagree with what it reads); rollover is deliberately deferred. Categorization is **rules-before-model**, the email feedback loop verbatim: `spending_rules` written by one-click "always file <merchant> here" decide first, a conservative keyword table second, batched **validated-labels-only** model garnish last (descriptors are hostile external text), and user hand-sets are never overwritten. `build_my_budget` drafts targets from code-computed aggregates (the model never sees raw rows) through the D17 suggest-and-apply gate. Budgets are per-user and private with no grants path — joint budgets are honestly deferred (Q-household-budget), not half-shipped. Everything but the drafting and coaching works with no model configured (D13's value-without-AI, kept). Full design in `docs/MONEY.md` §3. — *Built (B2). The derived-view bet held: `Money::MonthSummary` holds no state, so no meter can disagree with the ledger. One thing the design didn't anticipate and the build settled: a refund nets inside its own envelope rather than counting as income (Q-splits-and-refunds' first half, answered), and an over-refunded envelope floors at zero.*

**D-money-coach. Money coaching is support, not advice — and faithfulness nudges are pace facts, never commentary.**
The D32 boundary translated to money: `money_coach` is a D29 chat tool (mode presets: buy-decision · spend less · money stress · plan the month) whose context is the code-built budget snapshot, Money goals, prior recaps, and — only when the D-career-signal timeline has data — an hours-of-work wage line, source named. The one guardrail that must not depend on model behavior doesn't: a code-appended not-a-financial-advisor notice opens every session (never sent to the model), the prompt forbids specific investment/tax/credit-product recommendations, and debt distress steers warmly to nonprofit credit counseling plus the app's own Debt/Rights letter tools (the 988 pattern). Tone contract: the coach defends the user's *own stated plan* back to them, never shames, offers the 48-hour wait as a move not a rule, and when the user says "buying it anyway," helps fit it in gracefully — the user disposes. `spending_review` is the facts half: code aggregates in, narrated review + ≤5 traceable cut candidates out, D28-routed to `cancel_subscription`/`negotiation_prep` prefilled. Watchers (`budget_pace`, `new_recurring_charge`, `price_hike`, `month_close`) are deterministic SQL over the mirror, per-envelope-per-month fingerprints, no-signal-no-nudge — no LLM in any signal path, no judgment nudges ever (the D36 lesson: an assistant that nags gets turned off). Full design in `docs/MONEY.md` §4–5. — *Built (B4 then B3 — the coach first, so the watchers' accepts could route into real tools). `Spending::Recurring` turned out to be the load-bearing piece: one cadence-and-amount detector serves both the new-subscription and price-hike watchers, which is why a hiked charge can't also masquerade as a new subscription. `debt_payoff_plan` (B5) inherits the same boundary as a plan tool.*
**D-passwords-vault. Credential is a vault container, not a primitive; secrets never enter a model prompt.**
Passwords join the sidebar's Vault group as a **Passwords** view over a new `Credential` model (named so because `passwords` routes are Rails 8 auth's reset flow) on the **Album precedent**: `belongs_to :user`, `Visible`, **not** `Sectionable` — a login has no date, no done-state, no section, and must never reach a categorizer or a tool's context. No taggings means section-level grants structurally cannot cover credentials: sharing is **item-level only** (a shared-folder convenience is Q-vault-collections). The hard rule, enforced by construction: no credential secret ever enters a model prompt, a log line, an `AppError` context, or a background job. The agent endgame rides this vault — a per-item, off-by-default agent dial (D9-style visible configuration) will let agents use delegated credentials through code actuators that hand the model "signed in as …", never the secret. Full design in `PASSWORDS_PLAN.md`. — *Built (waves 1–5: crypto core and CRUD, TOTP/kinds/import/export, sharing with item-key rotation on revoke, the health panel, emergency access). Sharing is read-only for grantees, and `kind` turned out to be immutable after creation because it's sealed into the ciphertext's AAD. The agent dial (W6) waits on agent actuators.*

**D-vault-crypto. Vault secrets get envelope encryption keyed off the login password; at rest, the server cannot read them.**
A deliberate departure from the defer-hardening posture (D10/D14): the AR-encryption keys live in `storage/` next to the database on purpose, which is right for API keys and fatal for a password manager — a backup holder or a household admin would read every password, and "self-host instead of 1Password" is only credible if at rest the box holds nothing that opens the vault. The standard key hierarchy, server-side (not zero-knowledge — reveals transit the app; the threat model in `PASSWORDS_PLAN.md` §3 says so): per-user **vault key** stored only wrapped — under a KEK from the **login password** and under a KEK from a shown-once **recovery code**; a per-user RSA keypair (private key under the vault key); a per-credential **item key** encrypting secret fields (AES-256-GCM), wrapped to the public key of every reader in `credential_keys` — the owner is just the first keyholder, so sharing is another row, not another mechanism, and there is exactly one decrypt path. **Unlock rides sign-in**: the session controller derives the KEK while it briefly holds the password and stashes the vault key in an encrypted HttpOnly cookie (12h window; Lock is a button), so the unwrapped key never rests server-side. Two data tiers: metadata (name/username/url) uses the existing AR `encrypts` and stays listable while locked; secrets are vault-locked. Accepted costs, knowingly: password *change* rewraps seamlessly, password *reset* without the recovery code loses secrets (metadata survives; the reset flow gains a recovery-code step); grantees need initialized vaults; exports of secrets are in-request only (key material never transits the job queue); crypto is plain OpenSSL — PBKDF2 at OWASP iterations, no native gems, KDF params stored per-keyring so argon2id later is a data migration. Full design in `PASSWORDS_PLAN.md`. — *Built. The build also closed a pre-existing gap it depended on: the app had no change-password form at all (reset-only), and reset is exactly the flow that can't rewrap — so Settings grew one. A real nonce-based CSP shipped with it, since XSS is what turns a server-side vault into no vault.*

**D-recipe-primitive. Recipe is the eighth primitive; ingredients are rows, method is prose; recipe books are containers.**
Recipes get a top-level **Recipes** view in the sidebar's vault group (the Photos/Documents pattern), not an eighth section — D3's seven are locked and food isn't one life-area: a recipe multi-tags into Health, Money, People, and Hobbies like every other primitive. `Recipe` is `Visible` + `Sectionable`, and it splits its own body deliberately: **ingredients are structured rows** (`recipe_ingredients` with quantity/unit/item, a normalized `item_key`, and always the `raw` line as typed) because the pantry match, the grocery list, and scaling all key off quantities, while the **method stays prose** because nothing joins to step 4. Capture is a paste: one textarea, one ingredient per line, parsed deterministically by `Recipes::Parse` — no model call is ever needed to save a recipe, and because `raw` is kept the round-trip is lossless, so a line the parser reads badly still reads right on screen. **Recipe books are containers on the Album precedent** (D-photos-primitive): user-owned curation, one recipe in many books, `Visible` but not `Sectionable`, and `Recipe` takes the same fourth OR-branch — a grant on a book exposes the recipes in it, guarded by `grantor = recipe owner` so a future collaborative book can't leak a contributor's. Cooking is *logged, not tracked*: one "Cooked it" button stamps a date and a count, which is what the later rotation watchers read; no ratings, no timers, no streaks. Scaling is a link (`?servings=8`), not JavaScript — arithmetic only, formatted back into kitchen fractions, with unquantified lines passed through untouched. Full design in `RECIPES_PLAN.md`. — *Built (W1–W4: the primitive and its parser, books and household sharing, public links, and import). Two refinements landed with import: component dividers ("For the sauce:") are `heading` rows — in the list where the cook expects them, out of everything that shops or scales, and out of the `item_key` column the pantry match will read; and importing splits the work so the model only ever re-emits ingredient *lines* while the app's parser reads the numbers, which keeps one implementation of the arithmetic on every path. The pantry (D-pantry) and the rest of the AI wave are designed and planned.*

**D-share-link. Read-only public links are the first sharing path that leaves the household — allowlisted, unguessable, revocable.**
Every earlier sharing path was household-only by construction (`AccessGrant` validates a shared household), but a recipe's natural audience includes the sister in another state and the friend who asked at dinner — people who will never have an account on this box, and telling the target user to make them one is how a household goes back to a website. So `share_links`: a row per link, `/s/:token`, rendered on a bare layout with no navigation, no section chips, no email addresses, and no way further in. Narrow on purpose, and that narrowness *is* the decision: the subject type is allowlisted (`ShareLink::SHAREABLE_TYPES = Recipe, RecipeBook`) in the model and again in the controller's lookup table, because an unauthenticated read path must never become a generic one a later feature can point at a medical document; the 24-character token is the whole authorization; revoking is deleting the row; expiry is optional and evaluated at request time; `X-Robots-Tag: noindex` keeps a forwarded link out of search. Links stay visible objects the owner made (D9) — listed on the item with their label, view count, and last view. A book link opens the book *and* its recipes under the same token, guarded by the same owner rule as the grant clause. Public links are deliberately **outside** `visible_to`: they never widen what a signed-in user can see. — *Built. When photos or documents want public links, they join the allowlist and inherit the plumbing rather than growing a second mechanism.*

**D-pantry. The pantry is a container whose grant exposes its contents; the recipe match is deterministic SQL.**
Designed with the recipe box, built in its W4, and recorded now because the AI wave's shape depends on it. A pantry is a fast-churning list where per-item grants would be absurd, so it reuses the container-grant pattern a third time: one `Pantry` row per user (lazily created, `Visible`), `pantry_items` beneath it, and "share with the household" is the existing bulk-grant button. The important half is what stays out of the model: scoring a recipe against the pantry is **plain SQL over `item_key`** — the fraction of non-optional ingredients present — so "what can I make tonight" works on an instance with no model configured at all, and the LLM is left doing what it's for (picking among the top few, explaining, suggesting a swap). Same for the grocery list: union the ingredients, merge by `item_key`, subtract the pantry, group by aisle — no model call anywhere. The D20 watcher discipline, applied to dinner. — *Designed; W4/W5 of `RECIPES_PLAN.md`.*

**D-chat-shell. The chat surface has two layouts — `screen` and `panel` — and on a phone it is always `screen`.**
The D29 partial has two hosts that want opposite things: a dedicated conversation page should own the viewport (one scroller, composer welded to the bottom, chrome cut to a compact bar), while the panel embedded in a task page (D30) is a card in a flowing document and must stay one. Today it is neither — a `max-h-[calc(100dvh-20rem)]` scroller inside a card inside the scrolling page, which is two nested scrollers, a magic number that is wrong on every device, and a composer whose position depends on scroll state. So `_chat.html.erb` takes a `layout:` local (`:screen`/`:panel`, defaulting to the constrained case) and the height rules live in `.chat-screen`/`.chat-panel` atoms beside the existing chat set, not in per-view utilities. The corollary is the load-bearing half: **an embedded chat panel is never good on a phone**, because a card that is itself a scroller inside a scrolling page is precisely the bug — so below `sm` the task page's panel collapses to an entry point that opens the conversation full-screen (`GET /tasks/:id/conversation`, rendering with a possibly-nil run exactly as the panel already does), and stays inline from `sm` up. Chrome folds with it: below `lg` a `:screen` chat gets a compact bar (back, title, overflow menu) holding New session, Delete, and Save a recap, instead of a page header plus a three-line recap footer competing with the composer for the bottom of a phone. Full design in `CHAT_PLAN.md`. — *Built, with one correction: the viewport arithmetic lives on `.chat-page` (viewport − `--app-header-h` − `--keyboard-inset`) and `.chat-screen` is `flex-1 min-h-0` inside it, which is what lets a desktop page header sit above the screen without pushing it out. The layout's `min-h-screen` also had to go for a bleed page — it stacks a full viewport under the mobile header, so the document scrolled by exactly the header's height, which is the second scroller this decision exists to remove. The planned `chat-scroll` sentinel rewrite was dropped as wrong: an IntersectionObserver can't tell "the reader scrolled away" from "content grew below them", which is the only thing the `autoScrolling` flag is for.*

**D-chat-optimistic. A sent message renders locally before the server hears about it, and the server answers with an append, not a page.**
`ToolRunMessagesController#create` currently ends in `redirect_to run`, so every turn morphs the whole document and nothing happens on screen between the tap and the response — a few hundred milliseconds to a couple of seconds of a screen that looks like it ignored you. Two halves, and they belong together: the `chat-input` controller appends a user bubble from a `<template>`, clears the box, drops in the thinking indicator and scrolls, all synchronously *before* the fetch starts; and the server responds with a Turbo Stream append of the persisted turn instead of a page, with `ChatTurnJob` likewise broadcasting an append rather than `broadcast_refresh_to`. Because the transcript stops being re-rendered wholesale, scroll position, keyboard state, and a correctly-scoped `aria-live` announcement all come for free. The two are reconciled by a client-generated token: the optimistic bubble is `id="msg-<token>"`, the form posts the token, the server's append targets the same id, so Turbo replaces the placeholder instead of duplicating it. A failed POST leaves that bubble marked "Not sent" with a retry and **the user's text intact** — strictly better than today, where a failure loses the draft. Non-JS is unaffected: the form still posts, a non-stream request still gets the redirect, and the optimistic path is an enhancement over a working form, the same posture the send button's dimming already takes. — *Built, and half of it deliberately not: the server still answers with a redirect and the page still morphs. A turn changes more than the transcript (the composer's lock, the chips, the recap affordance, the retry button, the indicator), and five targeted streams would have traded a large regression surface for nothing the reader can see — while everything the reader *can* see, the gap between tap and response, is closed on the client alone. The token survived as a `client_token` column and is what makes the morph match the drawn bubble to the server's turn instead of swapping one for the other. One ordering fact is load-bearing: Turbo captures the request body when it constructs the submission, so the token is stamped on `submit` and the composer is cleared on `turbo:submit-start` — clearing it a moment earlier posted an empty message, a bug only the real browser found.*

**D-chat-stream. The reply streams token-by-token, buffered, and degrades to today's behavior when the endpoint can't.**
A long tutor explanation is ten to thirty seconds of three bouncing dots while the model is producing text we throw away. `Llm::Client#chat` gains a streaming mode — an SSE reader over the `Net::HTTP` we already own, no vendor gem (D14) — used on the chat path only, since every other tool parses a complete JSON document and has nothing to gain. `ChatBase#reply!` creates the assistant message row **empty and first**, then fills it, so each flush is a Turbo Stream `update` of one bubble by id. Two guardrails are mandatory, not optional: **buffer** (one broadcast per token would push thousands of messages per reply through SolidCable — flush on a ~80ms timer or a sentence boundary), and **degrade honestly** (an endpoint that doesn't do SSE falls back to the existing single-shot call and the dots, detected rather than asked about, because a self-hosted Ollama on someone's laptop must not be broken by a nicety). A mid-stream failure keeps whatever arrived and appends the existing notice row — the posture `ChatTurnJob` already takes, so a truncated reply is visible rather than vanished. — *Designed; W4 of `CHAT_PLAN.md`.*

**D-chat-index. Chat runs get an index, because a conversation you can't get back to is write-once.**
`config/routes.rb` mounts `resources :tool_runs, only: %i[ show destroy ]` — there is no index anywhere in the app, and the only route back into a past conversation is a link somebody remembered to hand-place (the Health panel's "pick it back up" for the last check-in is the entire recall surface). So every other conversation is effectively write-once: you have it, you navigate away, and it is unreachable until `PruneChatTranscriptsJob` deletes it at ninety days. The continuity is meanwhile *already built* — `ToolRun#previous_recap` renders "Picking up from last time —" at the head of a transcript — so the app implements resuming a conversation and gives the user no way to ask for it. `GET /conversations` lists chat-kind runs (owner-only, newest first, last turn as preview, grouped or filterable by tool, since "my tutor sessions" and "my check-ins" are different drawers), `tool_runs/new` leads with "continue where you left off" when recent runs exist, and the sidebar gains an entry — which is also what makes the chat tools findable at all, rather than reachable only from whichever section panel happens to link them. Recorded as a decision rather than a bug because it is a premise of `CHAT_PLAN.md`: the surface is benchmarked against apps whose *first screen is the list of conversations*, and one route plus one query is the cheapest thing in that document. — *Built. `/chats` lists every chat run newest-turn-first (ordered by a correlated `MAX(id)` subquery rather than `created_at`, so a conversation you returned to today sorts above one you started today and abandoned), with two queries for the whole page instead of two per row; a task-bound run links to its task, not to a run page; and the filter row only appears once there is more than one kind of conversation to tell apart.*

**D-task-celebration. Finishing a task gets a real celebration; the server sizes it, the client draws it, and one click turns it off.**
The Organize mode's honest weakness is that a well-kept list is a chore with no payoff — the moment worth feeling is the checkbox, and until now it was a page reload. So completion is a party: confetti from two corner cannons and a banner that pops, escalating by tier. The mechanics matter more than the sparkles. **The server decides** (`Tasks::Celebration`) because completion is a redirect (`button_to` → PATCH → `redirect_back`), so an animation started at click time would be wiped by the navigation half a second later; the verdict rides the flash as JSON (`flash[:celebrate]`, a data key `Ui::FlashComponent` refuses to render as a banner) and the page that comes back plays it. **The tier is counted, never inferred by a model**: ordinary task → confetti; a streak the copy knows about → more; the last open step of a Goal → fireworks; nothing left that today would put in front of you → the full works. No model call, no new table, no per-completion write beyond the one already happening. **It fires from `tokenValueChanged`, not `connect`**, because the app morphs on redirect-to-self (the layout's `turbo-refresh-method`): after the first celebration the rig is already in the DOM and `connect()` never runs again, so a fresh random token per celebration is what makes the second, third, and tenth task of the day feel the same as the first. Motion is bounded by two switches the user actually holds: `prefers-reduced-motion` drops to a banner that fades, and a Settings toggle (`users.celebrations`, default on) turns the whole thing off — a treat you can't decline is a nuisance, and D9's rule (visible, user-controlled, never a hidden default) covers delight as much as access. — *Built: `Tasks::Celebration`, the `celebration` Stimulus controller, the `.celebrate-*` atoms, and the Settings card. Every completion path shares it — the board, the list rows on Today, and "Save & complete" on the answer card.*
